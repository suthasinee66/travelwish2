# TravelWish quantitative evaluation (offline)

This is an **offline verifier**. It does not call Gemini, GPT, Claude, Google Places, Routes or Supabase and does not generate 135 plans automatically. Export actual planner results as JSON with the schema in `comparison/plan_runs.example.json` (replace every placeholder and illustrative 0).

## Run

```sh
npm run eval:plans -- comparison/plan_runs.json
```

Output:
- `comparison/plan_evaluation/results.csv`: one row per plan
- `comparison/plan_evaluation/results.json`: full audit fields, pass/fail/unknown counts

## Important methodology

- `verified=true` must be based on a verifiable independent place record, not on the model's own statement.
- A missing value is **unknown**, not a pass; percentage denominators include unknown. For example `PVR` = verified / all places. Report unknown counts as well.
- `profile_match` is a *metadata-based consistency check*, not behavioral ground truth. It currently passes when at least one specified known attribute matches; adapt the threshold and freeze it **before** experiment runs.
- `preference_coverage` counts profile labels found across attraction metadata.
- `time_feasibility` is a basic per-stop window and duration check; it is **not full schedule feasibility**. For rigorous temporal validation additionally verify travel feasibility between consecutive visits, opening hours for the correct date, weekday exceptions, waiting and transport mode.
- `budget_status` checks the sum of all entered `cost_thb` only. Include transport, accommodation and per-person vs group allocation before claiming real budget compliance. Missing costs yield unknown.
- `province_consistency` uses a supplied province string. Verify province independently (such as geocoding/authoritative administrative boundaries); do not trust model-supplied text.
- `constraint_satisfaction` is an explicit checklist. Allergy and other special restrictions require independently validated evidence.
- `final_plan_pass` requires verified places, each per-stop timing check, and all specified hard constraints passing. The strictness is a proposed TravelWish operational definition, not the original TravelPlanner benchmark score.
- Round counts, input-output prompts, generation configuration and dataset snapshots must be recorded to reproduce comparison.
- For TDMC Precision/Recall use **independent relevance ground truth**; do not evaluate the ranking against labels generated by the same ranking method.
- This module does not modify site runtime or production planner.

Reference framework: Xie et al. (2024) TravelPlanner for machine-checkable hard constraints; Lin et al. (topic diversity and accuracy); Lee et al. (diversity, popularity and travel distance). Formula details used here are TravelWish adaptations; do not attribute them verbatim to those works.

## Research protocol

1. Freeze a place dataset snapshot, travel dates, budget definitions and 3 user profiles × 3 provinces.
2. Run 3 models using an identical input payload and candidate pool per scenario, with 5 separate generations each (135 planned attempts).
3. Export real outputs and metadata to `comparison/plan_runs.json`; do not treat the example as real data.
4. Run the offline validator and analyze outcomes by case, province, model, and run.
5. Report average, standard deviation, failure and unknown proportions, along with sample sizes.

**Security:** Some legacy root-level import scripts contain a credential inline. Rotate any exposed Supabase service-role credentials and migrate those scripts to environment variables before sharing or using the repository further.
